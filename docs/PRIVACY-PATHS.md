# Privacy paths: how a frame, photo or clip could leave as clean, and the test that closes each one

This is the audit behind the guarantees on [Privacy](concepts/privacy.md). It has one row for each way found for a file to be delivered without having been analysed or blurred. A row names the path, what closes it, and the tests that fail if the path opens again.

`tests/test_privacy_paths.py` holds the tests written for this audit (their names carry a P and a number). The other tests are older. A test named in the table that no longer exists fails `tests.test_privacy_paths.Docs`.

From the repository root, `python3 -m unittest tests.test_privacy_paths` runs the tests written for this audit and checks that every test the table names exists; the whole suite (`python3 -m unittest discover -s tests -t .`) runs them all. The table is a record of what was looked for. It is not a proof that no other path exists.

## Found and fixed in this audit

- A video that stopped decoding partway raised PyAV's own error out of `analyze` and `render`. The error was not typed, and with the engine in a worker it was a crash that stopped the whole batch. Both calls now raise `UnsupportedMedia` with code `error.media.damaged`, and the batch goes on. Nothing was ever written as clean, so the fault was in how the error was handled, not in what was delivered.
- A photo damaged after its analysis (same size and time) raised a bare `OSError` from `render`, which the Studio reported as "cannot write to the folder". It is now `error.media.damaged`.
- The source was compared with its fingerprint only at the start of a render. A file replaced while the output was being written could be delivered with the boxes of the old one. `render_video` now takes a `before_commit` callback that runs when the partial file is complete, and photos check again before the rename. Both raise `SourceChanged` and leave nothing.

The family of these failures: errors from outside the engine that were not typed (PyAV, Pillow, the operating system) at each point where a file is opened (analysis, render, import, preview, upload); one-time checks of the source or of the analysis (the start of a render, the plan before a render); and every route that writes a final name (video, photo, comparison video, reports). Previews, thumbnails and the comparison video also read the source or the output, and they never write an anonymised file.

- A photo with something blurred kept almost all its EXIF, including the maker note, which cameras use for a full-size preview of the picture as it was before the blur (and for the serial number). A JPEG's own XMP, comment and IPTC segments had not been checked. The fix is the class of the failure: a list of what is kept instead of a list of what is removed (GPS). See row 12. The public photos of the benchmark (`bench/data/plates/openalpr-eu`) carry an image inside their EXIF, the camera's thumbnail. The old byte-copy path delivered it, and now none of them does. A photo with nothing to blur is cleaned too, so one batch does not deliver some photos with a serial number and others without. The pixels are the same, and a JPEG keeps its image data byte for byte.
- A second review round closed these: thumbnails of another analysis, stale previews and stale settings at render time, areas that draw nothing, a source fingerprint with content, files at the borders (damaged, too big, too many images), the unused second render path (removed), leftovers of a killed worker, and text from a visitor reaching a header or a spreadsheet. Each has its tests in the table above. The saved analysis format moved to version 3 along the way (it holds the new fingerprint), so an analysis saved before 2.1 is refused with `error.analysis.version` and has to be made again. Version 3 is also the format of 2.1 and 2.2, so an analysis saved by 2.1 loads in 2.2.
- Before 2.2, an item the detectors were not sure about was exported as decided, which by default meant visible. The API said so in every result and the Studio asked. 2.2 changed the rule: such an item is blurred when it is placed like a plate or a face, and the others are counted in a warning at every render (row 19).

## By design, so nobody takes it for a hole

- What was looked for is what the user chose: faces, plates, or both, never neither. The report lists the items found and what was done to each. The PDF and CSV reports do not say which classes were searched (the JSON report's `options` does), so a file analysed for plates only is a file with its faces untouched.
- A face or plate the detectors do not find is not found, and it is neither blurred nor listed. **Review** and **Add missed area** exist for that, and [Accuracy](accuracy.md) says how often it happens. The known limits (framed portraits, plates on something that is not detected as a vehicle, very small faces) are on [Limits](accuracy.md).
- Decisions live in the saved analysis (the JSON written by `Analysis.save`). Editing that file by hand changes what is rendered.
